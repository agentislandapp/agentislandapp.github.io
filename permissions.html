Why your Claude Code allow rules keep asking anyway

You allowed npm test. It is still asking. The reason is that allow rules match the whole command string as a prefix, so a single cd in front of the command defeats the rule you wrote.

Written while building AgentIsland, which mirrors this matching to decide what to put on screen. Everything below was checked against the real files rather than the docs.

The order the checks run in

Three separate gates decide whether you get asked, and they are not the same gate. In order:

GateWhat it does
Deny rulesChecked first. A match stops the call whatever else is set.
Allow rulesChecked next. A match runs the tool with no prompt.
HooksA separate mechanism entirely. A PreToolUse hook can hold the call and answer for you.

Two consequences people trip over constantly, both of which follow from that ordering:

Deny beats allow, always. You cannot re-permit something with a broader allow rule — the deny is read first and nothing later overrules it. This is the property that makes deny rules worth writing: they hold even in modes where an approval prompt would never have appeared.
Bypass mode does not bypass hooks. Permission mode and hooks are separate gates, and bypass only opens one of them. A PreToolUse hook that asks will still stop you in bypass or auto mode — and the prompt it produces can look exactly like a normal permission prompt, which is why "it suddenly started asking again" so often turns out to be a hook someone added weeks ago.

The prefix rule, which is the actual answer

An allow rule looks like Tool(pattern). The pattern is matched against the tool's input, and there are only three shapes:

RuleMatches
Bashevery Bash call, whatever the command
Bash(*)the same thing, written explicitly
Bash(npm test)exactly the string npm test, nothing else
Bash(npm test:*)any command starting with npm test

The trailing :* is a prefix match on the entire command string. Not on the program name, not on each command in a chain — on the whole string, from the first character. Which means:

Rule:    Bash(npm test:*)

npm test                  ✅ matches — starts with "npm test"
npm test --watch          ✅ matches
cd frontend && npm test   ❌ no match — starts with "cd"
NODE_ENV=test npm test    ❌ no match — starts with "NODE_ENV"
(cd frontend; npm test)   ❌ no match — starts with "("

Nothing here is a bug. It is a prefix comparison doing exactly what a prefix comparison does. But it explains the single most common complaint about this system: the agent chains a cd in front of a command, and your carefully written allow rule silently stops applying. You did not do anything wrong; you wrote a rule against a shape the agent then stopped using.

What to do about it

  • Match the program, not the invocation. Bash(npm:*) survives flags and arguments that Bash(npm test:*) does not. Broader, but broad in a direction you can reason about.
  • Ask the agent to stop chaining. A line in CLAUDE.md saying to run commands from the repo root rather than cd-ing first removes the problem at the source, and is more reliable than trying to enumerate every prefix.
  • Do not try to enumerate. cd a && npm test, cd b && npm test, and so on is an infinite list, and every entry is a rule you have to keep correct forever.

Where the rules are actually read from

Allow and deny rules are merged from more places than most people expect, and a rule in one file will not show up when you look in another:

  • ~/.claude/settings.json — your own, applies everywhere
  • <project>/.claude/settings.json — checked into the repo, applies to everyone working on it
  • <project>/.claude/settings.local.json — yours, for this repo, not checked in
  • ~/.claude.json — the one people miss. Session approvals ("don't ask again") land here under projects → <path> → allowedTools, not in any settings file
That last file explains a specific confusion: you clicked "don't ask again" once, months ago, and now cannot find the rule anywhere in your settings. It is in ~/.claude.json, keyed by the project's absolute path — so it also silently stops applying if you move or rename the directory, or reach it through a different symlink.

What a blocking hook can actually do

A PreToolUse hook is not just a notification. It runs before the tool, and the call waits for it. Whatever JSON it prints becomes the decision, and printing {} means "no opinion" — the normal terminal prompt appears, exactly as if the hook were not there.

That fallback is the whole design, and it is worth copying if you write one of your own:

  • Fail open, never closed. If your hook cannot reach whatever it asks, print {} and let the terminal prompt happen. A hook that fails closed turns a bug in your script into a session that cannot run anything.
  • Never exit non-zero for an ordinary failure. Print {} and exit 0.
  • Stay under the timeout. Claude Code gives a hook 55 seconds. If yours waits on something, give it a shorter deadline of its own — ours uses curl -m 52 — so it always answers before the harness stops waiting, rather than being killed mid-thought.

A worked example: making a destructive command impossible

Deny rules are checked before the permission mode, so this holds even in bypass or auto mode, where no prompt would ever have appeared:

{
  "permissions": {
    "deny": [
      "Bash(sudo date:*)",
      "Bash(sudo systemsetup:*)",
      "Bash(rm -rf /:*)"
    ]
  }
}

Worth knowing the limit of this, though, because it is easy to over-trust: deny rules constrain the agent's own tool calls. They do not constrain a script the agent wrote and then ran. If the agent writes a Python file that reads your .env and connects to production, that is Python reading a file it is allowed to read, and no rule here sees it. The boundary that holds in that case is what the credential itself is permitted to do — a read-only database user, a reader-role service principal — not what the agent is permitted to type.
